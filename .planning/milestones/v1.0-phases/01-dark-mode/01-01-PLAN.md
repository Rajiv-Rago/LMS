  <behavior>
    - getStoredTheme returns "system" when localStorage has no "theme" key
    - getStoredTheme returns "dark" when localStorage has "theme" = "dark"
    - getStoredTheme returns "light" when localStorage has "theme" = "light"
    - getStoredTheme returns "system" for any invalid localStorage value
    - setStoredTheme("dark") sets localStorage "theme" to "dark"
    - setStoredTheme("light") sets localStorage "theme" to "light"
    - setStoredTheme("system") removes the "theme" key from localStorage
    - resolveEffectiveTheme("dark") returns true (isDark)
    - resolveEffectiveTheme("light") returns false
    - resolveEffectiveTheme("system") returns true when OS prefers dark
    - resolveEffectiveTheme("system") returns false when OS prefers light
    - Cycling from "light" produces "dark", from "dark" produces "system", from "system" produces "light"
  </behavior>
  <action>
    **globals.css changes (do this FIRST):**
    1. Add `@custom-variant dark (&:where(.dark, .dark *));` AFTER `@import "tailwindcss"` and BEFORE `@plugin "@tailwindcss/typography"`. Order matters -- the typography plugin must see the custom variant.
    2. Replace `@media (prefers-color-scheme: dark) { :root { ... } }` with `.dark { --background: #0a0a0a; --foreground: #ededed; }`. This prevents dual-system conflict where the media query and class system disagree.
    3. Do NOT add transition classes to body CSS. Transitions are added via JS after first paint (Task 2).

    **useTheme hook (lib/hooks/useTheme.ts):**
    Export a `ThemeMode` type: `"dark" | "light" | "system"`.
    Export pure helper functions (for testability): `getStoredTheme()`, `setStoredTheme(mode)`, `resolveEffectiveTheme(mode)`, `applyTheme(isDark)`.
    Export the `useTheme()` hook that returns `{ mode: ThemeMode, cycle: () => void }`.

    Implementation per research patterns:
    - `getStoredTheme()`: Read localStorage "theme" key. Return "dark"/"light" if stored, "system" otherwise.
    - `setStoredTheme(mode)`: If "system", removeItem. Otherwise setItem.
    - `resolveEffectiveTheme(mode)`: "dark" -> true, "light" -> false, "system" -> matchMedia check.
    - `applyTheme(isDark)`: `document.documentElement.classList.toggle("dark", isDark)`.
    - Hook uses `useState` initialized from `getStoredTheme()`.
    - `useEffect` for applying theme class when mode changes.
    - `useEffect` for matchMedia "change" listener when mode === "system" (cleanup on unmount or mode change).
    - `cycle()` callback: light -> dark -> system -> light. Calls `setStoredTheme` and `applyTheme` synchronously for immediate feedback.
    - Mark as `"use client"`.

    Mock `localStorage` and `window.matchMedia` in test setup.

    **FOUC script update (app/layout.tsx):**
    Update the inline script in `<head>` to handle three-way "system" support:
    ```
    (function(){try{var t=localStorage.getItem("theme");var d=t==="dark"||(t!=="light"&&matchMedia("(prefers-color-scheme:dark)").matches);if(d)document.documentElement.classList.add("dark")}catch(e){}})()
    ```

    Key difference from current: when `t` is `null` (system mode), it falls through to matchMedia -- same as before. But when `t === "light"`, it explicitly skips the matchMedia check and stays light. The current script already does `!t` for system, but the `t!=="light"` guard is more explicit for the three-way contract.

This can be a useEffect in a tiny client wrapper, or a second inline script with `requestAnimationFrame`. The key constraint: transitions must NOT be present during initial page load (prevents flash), only added after hydration for subsequent toggles.

    Recommended approach: Create a small `<TransitionEnabler />` client component rendered inside `<body>` that runs a useEffect adding `transition-colors duration-200` to `document.body`. This is the cleanest separation.
