  <behavior>
    User model soft-delete:
    - User.find() excludes documents where deletedAt is not null
    - User.findOne({ email }) excludes soft-deleted users
    - User.findById(id) excludes soft-deleted users
    - User.findById(id, null, { includeSoftDeleted: true }) returns soft-deleted users
    - Existing users without deletedAt (null default) are unaffected

    Auth session flow:
    - POST /api/auth/login returns auth cookie
    - GET /api/auth/me with valid cookie returns user data
    - POST /api/auth/logout clears auth cookie (returns Set-Cookie with empty value and immediate expiry)
    - GET /api/auth/me after logout returns 401

    Account deletion:
    - DELETE /api/users/me/delete with valid auth soft-deletes user (sets deletedAt)
    - After deletion, User.findById(userId) returns null (excluded by soft-delete filter)
    - After deletion, User.findById(userId, null, { includeSoftDeleted: true }) returns the user
    - Enrollment documents for deleted user are cleaned up (deleted)
  </behavior>
  <action>
    Write tests first, then fix.

    1. User model fix (lib/models/User.ts):
    Add the pre-find middleware hook identical to Course model's pattern, right after the userSchema methods and before the index definitions:
    ```typescript
    userSchema.pre(/^find/, function (this: mongoose.Query<unknown, IUser>, next) {
      if (!this.getOptions().includeSoftDeleted) {
        this.where({ deletedAt: null });
      }
      next();
    });
    ```
    Add a deletedAt index: `userSchema.index({ deletedAt: 1 });`

    2. User model tests (lib/models/User.test.ts):
    The existing file has model-level tests. Add a new describe block for soft-delete behavior:
    - Create user, set deletedAt to new Date(), save
    - User.find() should not return the deleted user
    - User.findById() should not return the deleted user
    - User.findById(id, null, { includeSoftDeleted: true }) should return it

    3. Auth session tests (__tests__/integration/auth/session.test.ts):
    New test file testing the full auth flow:
    - Login: POST /api/auth/login with valid credentials -> 200 + cookie
    - Me: Build request with token from login, call GET /api/auth/me -> 200 + user data
    - Logout: POST /api/auth/logout -> response has Set-Cookie header clearing the auth cookie
    - Note: Since route handlers are called directly (not via HTTP server), cookie behavior is verified by checking response headers, not actual cookie state. For /me after logout, test without token -> 401.

    4. Account deletion tests (__tests__/integration/account/deletion.test.ts):
    - Create user, create enrollment for user, call DELETE /api/users/me/delete
    - Verify user is soft-deleted (findById returns null, findById with includeSoftDeleted returns user)
    - Verify Enrollment documents for deleted user are cleaned up
    - Import Enrollment model to verify cleanup
    - If the delete route does not currently clean up Enrollment documents, add that cleanup to the route (Enrollment.deleteMany({ student: user.userId }))

    __tests__/integration/queue/worker.test.ts

  <behavior>
    - Worker processes a pending job by calling its registered handler
    - Completed job has status "completed" and result set
    - Failed handler (throws error) causes job retry with status back to "pending"
    - Job that fails maxAttempts times gets status "failed" with error message
    - Job with unknown type gets status "failed" with "No handler registered" error
    - Worker does not exceed MAX_CONCURRENT jobs
    - Stale jobs (processing for >5 min) are reset to pending
  </behavior>
  <action>
    Write tests that exercise the worker's processJob and poll logic by directly manipulating Job documents in the test DB.

    Test approach:
    - Do NOT start the actual worker polling loop (it uses setInterval which complicates tests)
    - Instead, test the job processing logic by:
      a. Creating Job documents directly via Job.create()
      b. Registering test handlers via the handler registry
      c. Importing and calling the poll function (or processJob) directly if exported, OR testing via the full startWorker/stopWorker cycle with a short poll interval

    If poll/processJob are not exported, test through the public API:
    1. Register a test handler that resolves/rejects on demand
    2. Create a pending Job document
    3. Call startWorker(), wait briefly for poll to fire, stopWorker()
    4. Verify Job status changed

    More pragmatic approach: mock the handler registry, create jobs, call worker functions:

    - Import Job model, use createTestUser for userId
    - Register a mock handler via the handler system:
      ```typescript
      // Register a test handler
      const mockHandler = jest.fn().mockResolvedValue({ testResult: true });
      ```
    - Create Job document: { type: "test.mock", status: "pending", userId, data: {}, maxAttempts: 3 }
    - Start worker, wait ~3 seconds for poll, stop worker
    - Verify: job.status === "completed", job.result contains testResult

    For retry testing:
    - Register handler that throws on first call, succeeds on second
    - Create pending job, start/stop worker with enough time for retry
    - Verify: job.attempts incremented, eventually completed

    For stale job reset:
    - Create job with status "processing" and startedAt 6 minutes ago
    - Run poll
    - Verify: job reset to "pending"

    Note: Use jest.setTimeout(30000) for these tests since they involve real polling delays.
    Import { startWorker, stopWorker } from "@/lib/queue/worker".
    After each test, stop the worker to prevent interference.
